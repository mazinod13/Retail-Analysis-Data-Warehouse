# Warehouse design notes

Design rationale for the star schema in [01_create_dw_tables.sql](01_create_dw_tables.sql). The DDL keeps only short inline comments; the reasoning lives here.

---

## The grain

> **One row in `fact_sales` = one product line on one order.**

That single sentence drives every other decision in the schema. It's the lowest level of detail available in the source system, which means every other level — order, day, month, category, region — can be aggregated up from it. You can always roll up; you can never break back down.

Declaring the grain before writing any DDL is the first step of Kimball's dimensional design process, and it's the question I'd expect to be asked first about this model.

---

## Structural decisions

### Why a separate schema, not a separate database

The warehouse lives in a `dw` schema inside the same database as the OLTP tables. That lets the ETL join source tables to dimension tables in a single query with no cross-database connection, and it means the entire warehouse can be dropped and rebuilt without touching the source data.

Schemas also give real namespacing: read-only access can be granted on `dw` independently, and `DROP SCHEMA dw CASCADE` cleanly removes everything derived.

### Why `TEXT` instead of `VARCHAR(n)`

In Postgres the two are identical in performance. My first draft re-declared widths in the warehouse and several were narrower than the source columns — `dim_product.name` at 100 against a source of 150, `dim_store.city` at 50 against 100, and five more. That would have failed at load time with `value too long for type character varying`, or worse, truncated silently had I used explicit casts.

These values were already validated by constraints at the source. Re-constraining them here buys nothing and adds a failure mode.

### Surrogate keys

Every dimension has a synthetic integer primary key (`customer_key`, `product_key`) that is **not** the OLTP id. The source id is retained alongside it as the natural key.

Three reasons: surrogate keys let one source record have multiple dimension rows (which is how Type 2 history works), they insulate the warehouse if the source system ever renumbers, and integer joins are fast.

The keys use `GENERATED BY DEFAULT AS IDENTITY` rather than `GENERATED ALWAYS`. `ALWAYS` rejects explicit values, and the unknown-member rows need to be inserted with a hardcoded `-1`.

`dim_date` is the deliberate exception — see below.

## Dimensions

### `dim_date`

The only dimension with no source table; it's generated from a date range rather than loaded.

It's also the only dimension that uses a **smart key**: `date_key` is the date encoded as `YYYYMMDD` (`20261225`) instead of a meaningless surrogate. This is standard Kimball practice for dates, because it makes fact rows readable while debugging and lets you range-filter dates on the fact table without joining the dimension at all.

Fiscal year is defined as running **February 1 – January 31**, the common retail convention. That's a choice, not a fact — the ETL that populates the column is where to change it.

### `dim_customer` — Slowly Changing Dimension, Type 2

Type 2 means an attribute change creates a **new row** rather than overwriting the old one, so a sale made in 2024 stays attributed to the city the customer lived in at the time. Overwriting (Type 1) would silently rewrite history: every past sale would appear to have happened at the customer's current address.

Two consequences show up directly in the DDL:

**1. `customer_id` is deliberately not `UNIQUE`.** One customer legitimately has many rows here, one per version. My first draft had `customer_id INT NOT NULL UNIQUE`, which makes Type 2 impossible — that single constraint would have quietly reduced the dimension to Type 1.

**2. Uniqueness is enforced by a partial unique index instead.** What actually needs to be true is "at most one *current* row per customer," which a plain constraint can't express:

```sql
CREATE UNIQUE INDEX uq_dim_customer_current
    ON dw.dim_customer (customer_id)
    WHERE is_current;
```

The bookkeeping columns are `valid_from`, `valid_to` (NULL on the current row, meaning "still true"), and `is_current`.

**Which attributes to version on:** change detection should compare `city`, `state`, and `email`. It must *not* version on `age` — that changes for everyone every year and would churn the dimension annually for no analytical benefit. Attributes that change on a predictable schedule aren't slowly changing dimensions; they're derived facts.

### `dim_product`

The category hierarchy from the source is **flattened into this table** rather than kept as separate `dim_category` / `dim_parent_category` tables.

Keeping them separate would be a snowflake schema: it would rebuild the OLTP normalization inside the warehouse and throw away the performance benefit the star exists to provide. Yes, "Electronics" is repeated across hundreds of rows — that redundancy is the point. Dimensions are wide, denormalized, and read-optimized.

Flattening a self-referencing hierarchy is exactly what a **recursive CTE** is for, so the recursive query does real work in the ETL rather than existing as a showcase. `category_path` holds the full walked path (`'Electronics > Laptops'`), which is the natural by-product of that walk.

This is a Type 1 dimension — product attribute changes overwrite — so `product_id` *is* uniquely constrained here, unlike `customer_id`.

### `dim_store`

Straightforward. `opened_date` is retained because store age is a real analytical dimension — comparing a store opened last quarter against one open for four years is a category error unless you can filter on it.

### `dim_employee`

`manager_name` and `store_name` are denormalized rather than stored as keys. A report wants to display "Dana Reyes / Austin", not resolve two more joins to find out.

This dimension carries an **unknown member** at `employee_key = -1`, labelled "Online / No Salesperson". About 40% of orders are online and have no salesperson attached. A NULL foreign key in a fact table breaks inner joins and forces every downstream query to remember an outer join, so online sales point at an explicit row instead. The cost is one dimension row; the benefit is that every fact foreign key can be `NOT NULL`.

## `fact_sales`

**Grain: one product line on one order.**

### Degenerate dimension

`order_id` is stored as a plain column with no corresponding dimension table. It's an identifier with no descriptive attributes of its own, so a dimension would be an empty shell — but it has to be present, because the grain is the *line*, not the order. Without it you cannot count distinct orders or compute average order value.

### Cancelled orders are kept, not filtered

`order_status` is carried on the fact so cancelled sales (~7.5% of orders) can be excluded from revenue at query time, while the cancellation rate itself remains measurable. Dropping those rows during the load would make that question permanently unanswerable — and cancellation rate is a metric a retail business genuinely cares about.

### Derived measures are stored

`net_amount`, `cost_amount`, and `profit_amount` are all computable from other columns, so storing them is technically redundant. It's deliberate: computing them once at load time beats recomputing them on every dashboard query. This is the classic warehouse trade — storage and write complexity for read speed.

| Measure | Definition |
|---|---|
| `gross_amount` | `quantity × unit_price` |
| `discount_amount` | line-level discount |
| `net_amount` | `gross − discount` |
| `cost_amount` | `quantity × product cost` |
| `profit_amount` | `net − cost` |

### The grain is enforced by a constraint

```sql
CONSTRAINT uq_fact_sales_grain UNIQUE (order_id, product_key)
```

This mirrors the source system's `(order_id, product_id)` constraint and turns an accidental ETL re-run into a loud failure instead of silently doubled revenue. A grain declared only in a comment is a grain that eventually gets violated.

### No indexes — on purpose

The foreign key columns are intentionally left unindexed. Postgres doesn't create indexes on the referencing side of a foreign key automatically, and adding them here would be premature.

Index tuning with before/after `EXPLAIN (ANALYZE, BUFFERS)` comparisons is a later phase of this project, and that comparison is only meaningful if the "before" state is honest.

## Rebuilding

```bash
psql -U postgres -d retail_warehouse_db -v ON_ERROR_STOP=1 -f warehouse/00_drop_dw_tables.sql
psql -U postgres -d retail_warehouse_db -v ON_ERROR_STOP=1 -f warehouse/01_create_dw_tables.sql
```

Unlike the OLTP teardown, this one is cheap to run. Everything in `dw` is derived from the source tables and can be rebuilt by re-running the ETL — nothing here is a system of record.
